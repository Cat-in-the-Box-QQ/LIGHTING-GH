# 💡 LIGHTING-GH

เว็บคลังอุปกรณ์ไฟ (Lighting inventory) สำหรับทีมถ่ายทำ — ค้นหา กรอง ดูสเปก จัดชุดอุปกรณ์
และติดตามสต็อก เป็น static site ล้วน ไม่มี build step

Deploy บน **Vercel** (production deploy จาก branch `main` อัตโนมัติ)

---

## หน้านี้ทำอะไรได้บ้าง

| หน้า | หน้าที่ |
|---|---|
| `index.html` | Dashboard — สรุปจำนวนอุปกรณ์ แบรนด์ สต็อก และสัดส่วน RGB |
| `equipment.html` | รายการอุปกรณ์ทั้งหมด + ค้นหา/กรอง/เรียง + popup รายละเอียด |
| `fixture.html` | หน้ารายละเอียดอุปกรณ์หนึ่งรายการ พร้อมแหล่งอ้างอิงการตรวจสอบข้อมูล |
| `accessories.html` | คลังอุปกรณ์เสริม |
| `inventory.html` | มุมมองสต็อกแบบกางดู (available / reserved / in use / remaining) |
| `setbuilder.html` | จัดชุดอุปกรณ์ คำนวณกำลังไฟที่กิน น้ำหนัก กระแสไฟฟ้า และความจุแบตเตอรี่ (Wh) + runtime |
| `admin.html` | **Sign in** — `admin` เห็นเครื่องมือเพิ่ม/แก้ไข/ซ่อน/ลบ + แผงสถานะ Supabase, `crew` เห็นเฉพาะบัญชีตัวเอง + ปุ่มจอง |

## ข้อมูลมาจากไหน

ระบบมี 2 โหมด เลือกอัตโนมัติตอนโหลดหน้า:

1. **Supabase** (โหมดหลัก) — อ่าน/เขียนตาราง `fixtures` และ `accessories`
   เป็นข้อมูลกลางที่ใช้ร่วมกันทุกเครื่อง
2. **Local** (fallback) — อ่าน `data/*.json` แล้วเก็บส่วนแก้ไขใน `localStorage`

ถ้า Supabase ใช้ไม่ได้ (ตารางยังไม่ได้สร้าง / เน็ตหลุด / ตารางว่าง / CDN ถูกบล็อก)
เว็บจะถอยกลับมาใช้โหมด local อัตโนมัติเพื่อไม่ให้หน้าขาวเปล่า และจะแสดงป้ายสีเหลือง
บอกสถานะเสมอในหน้า `admin.html`

ดูรายละเอียดการตั้งค่าที่ [`supabase/README.md`](./supabase/README.md)

## แบตเตอรี่กับกำลังไฟ

เว็บแยกสองค่านี้จากกันชัดเจน เพราะความหมายต่างกันและเอาไปคำนวณคนละอย่าง:

| ฟิลด์ | หน่วย | ความหมาย | ใช้ทำอะไร |
|---|---|---|---|
| `power` | **W** | กำลังไฟที่อุปกรณ์ **กิน** | รวมเป็นโหลด คิดกระแสไฟ (A) |
| `batteryWh` | **Wh** | ความจุแบตเตอรี่ | คิดว่าเลี้ยงโหลดได้นานแค่ไหน |

รายการที่เป็นแบตเตอรี่หรือ power station (`type = power`, category เป็น
`Battery` / `Power Station`) ถือเป็น **แหล่งจ่ายไฟ ไม่ใช่โหลด** จึงไม่ถูกนับในกำลังไฟรวม
และไม่ถูกกรองด้วยเกณฑ์ "กำลังไฟสูงสุด"

ถ้า `batteryWh` ว่าง ระบบจะพยายามเดาจากข้อความที่มีอยู่:

```
3.6kWh LFP power station                          → 3600 Wh
3600W AC output / 7200W surge / 3600Wh capacity   → 3600 Wh  (จับ Wh ไม่จับ W output)
15 W (20 H.)  + power = 15                        → 300 Wh   (Astera Ax3)
```

**ถ้าเดาไม่ได้จะเว้นว่าง ไม่มั่วสเปก** — เช่น FXLION V-Mount ที่ยังไม่ทราบความจุแน่นอน
ให้กรอกเองผ่านหน้า Sign in ด้วยสิทธิ์ `admin` (มีช่อง "Battery Capacity (Wh)" พร้อมแสดงค่าที่ระบบเดาให้เทียบ)

## รันในเครื่อง

ไม่ต้อง install อะไร:

```bash
python3 -m http.server 8080 --bind 0.0.0.0
```

แล้วเปิด <http://localhost:8080/admin.html>

> ต้องเสิร์ฟผ่าน HTTP server ไม่ใช่เปิดไฟล์ตรง ๆ (`file://`) เพราะโค้ดใช้ `fetch()`
> อ่าน `data/*.json` ซึ่งจะโดน CORS บล็อกถ้าเปิดเป็นไฟล์

## เข้าสู่ระบบ (Sign in)

1. เปิด `admin.html` (navbar เรียก **Sign in**)
2. login ด้วยบัญชีที่ admin สร้างไว้ใน Supabase → Authentication → Users
   (ปิดการสมัครเองไว้แล้ว จึงไม่มีทางสร้างบัญชีจากหน้าเว็บ)
3. หน้าเว็บจะแสดงไม่เหมือนกันตามสิทธิ์ — ไม่มีขั้นอนุมัติ บัญชีใหม่ใช้ได้ทันที

| สิทธิ์ | เห็นอะไร |
|---|---|
| `admin` | ทุกแผง: การเชื่อมต่อ Supabase · สถานะการตรวจสอบ · คำแนะนำ · จัดการข้อมูล · ทีมงานทุกแถว (แก้ไข/ปิดใช้งาน) — และปุ่ม **แก้ไข / ซ่อน / ลบ** จะปรากฏใน popup รายละเอียดของหน้า Equipment กับ Accessories |
| `crew` | เฉพาะ section **ทีมงานและสิทธิ์** แถวของตัวเอง + ปุ่ม **จอง** ท้ายชื่อ |

> ปุ่มจองยังปิดอยู่ (`จอง — เร็ว ๆ นี้`) จนกว่าหน้าจองจะถูกสร้าง

ระบบเดิมใช้ PIN `1234` ฝังในโค้ด ซึ่งใครก็เปิด DevTools อ่านได้ — ถอดออกแล้ว
ตอนนี้ต้อง login ผ่าน Supabase Auth เท่านั้น

`SUPABASE_ADMIN_EMAILS` ใน `js/supabase-config.js` เป็น**ทางออกฉุกเฉินช่วงเปลี่ยนผ่าน**เท่านั้น
(ใช้เมื่ออ่านตาราง `members` ไม่ได้ เช่นยังไม่ได้รัน SQL) — ค่าที่ ship อยู่คือ `[]` ซึ่งแปลว่า
**ปิดทางนี้** สิทธิ์จริงต้องมาจากคอลัมน์ `role` ในตาราง `members` เสมอ

```js
window.SUPABASE_ADMIN_EMAILS = [];  // [] = ไม่ยอมให้ใครเป็น admin จากรายชื่ออีเมล
```

## ระบบจองอุปกรณ์

สถานะตอนนี้: **ใช้งานได้จริงทั้งเส้น** — ชั้นฐานข้อมูลรันบนโปรเจกต์จริงแล้ว,
ปฏิทินจองอ่านจากฐานข้อมูลจริง, **ฟอร์มสร้างใบจองบันทึกจริง**ผ่าน `create_booking()`,
การ์ดอุปกรณ์/อุปกรณ์เสริมมีปุ่ม **จอง** (หรือ **ดูคิว** ถ้าวันนี้เต็ม) ที่พาไปเปิดฟอร์ม
พร้อมรายการนั้นในใบจอง, Set Builder มีปุ่ม **จองชุดนี้** ที่แตกชุดเป็นรายชิ้น,
และปุ่ม **จอง** ท้ายชื่อในหน้า Sign in พาไปหน้าปฏิทินจองแล้ว

ยังเหลือฝั่ง admin: หน้าจัดการใบจอง (รับของ / ปักค้างคืน / ยกเลิก / ดู `v_booking_stale`)

กติกาที่บังคับไว้ที่ฐานข้อมูล (ดู [`supabase/README.md`](./supabase/README.md) หัวข้อ "ระบบจองทำงานยังไง")

| กติกา | ทำไม |
|---|---|
| จองได้วันเดียวต่อใบจอง พ้นวันนั้นของกลับคลังเอง | ไม่ต้องใช้ cron และไม่ต้องมีตารางคืนของ |
| จองเกินจำนวนที่มีไม่ได้ | trigger ล็อกรายชิ้นด้วย `pg_advisory_xact_lock` แล้วนับยอดจอง — สองคนกดพร้อมกันจะเรียงคิว ไม่ใช่ได้ของเกินทั้งคู่ |
| รายการที่ยังไม่ระบุจำนวน จองไม่ได้ | แสดง "ยังไม่ระบุจำนวน — จองไม่ได้" แทนเลข 0 เพราะ 0 แปลว่าของหมด ซึ่งไม่จริง (ตอนนี้อุปกรณ์เสริม 70 จาก 72 รายการยังไม่กรอก) |
| ของไม่กลับคลังจริง → admin ปัก `overdue` | ปิดจุดบอดของการคืนอัตโนมัติ เพราะระบบไม่มีทางรู้ว่าของหายไป |
| จำนวนที่ติดจองคำนวณจากใบจองเสมอ | **ห้าม**แก้คอลัมน์ `stock` — ไม่งั้นจะมีแหล่งความจริงสองก้อนแล้วตัวเลขเหลื่อมกันแบบตามแก้ไม่เจอ |

ยอดที่เห็นบนการ์ดมาจาก view `v_item_availability` ซึ่งเป็น**ก้อนเดียวกับที่ trigger ใช้ตัดสิน**
ผู้ใช้จึงไม่เจอเหตุการณ์ "หน้าเว็บบอกว่าเหลือ 2 แต่กดจองแล้วโดนปฏิเสธ"

### ปฏิทินจอง (`booking.html`)

หน้า Inventory ตอบได้แค่ว่า "วันนี้เหลือกี่ชิ้น" เพราะ view ข้างบนนับเฉพาะ
`booking_date = current_date` ทั้งที่งานจริงจองล่วงหน้ากันเป็นสัปดาห์
มุมมองล่วงหน้าจึงย้ายมาอยู่หน้าปฏิทิน

| | |
|---|---|
| มุมมองหลัก | รางเลื่อน 12 แผงเดือน (แผงละ 1 เดือน) เลื่อนซ้าย-ขวาได้ด้วยลูกศรข้างปฏิทิน / ลากเมาส์ / หมุนล้อ / ปัดบนมือถือ / กด ← → |
| มุมมอง "ปี (ภาพรวม)" | 12 เดือนย่อในจอเดียว กดปุ่มเดือนเพื่อเปิดแบบเต็ม |
| ช่องวัน | ขนาดปฏิทินปกติ แสดง**แค่เลขวัน + จุดกลมสี** — หนึ่งจุดต่อหนึ่งคนที่จองวันนั้น หลายคนจองจึงเห็นหลายจุด · วงแหวนแดง = มีของหมด · แดงปรุ = มีของค้างคืน · เหลือง = วันนี้ |
| กดวันที่ | แผงใต้ปฏิทินแสดง**ใบงานเป็นการ์ด** (คนจอง สถานะ ชื่องาน สถานที่ รายการอุปกรณ์ หมายเหตุ) พร้อมตาราง "รวมทุกใบจองของวันนั้น" ที่หักยอดทุกใบแล้ว จึงเห็นว่าเหลือให้คนอื่นอีกเท่าไหร่ |
| สีประจำตัว | ผูกถาวรกับแต่ละคน ไม่สลับเมื่อรีเฟรชหรือเมื่อมีสมาชิกเพิ่ม |

**sign in แล้วหน้าเว็บจะเปิดโหมด "ข้อมูลจริง" ให้อัตโนมัติ** (อ่าน `v_booking_day_detail`,
`v_item_stock` และ `members.color_hue`) · ยังไม่ sign in จะได้โหมด**ข้อมูลตัวอย่าง**
(`js/booking-demo.js`) ซึ่งสุ่มแบบ deterministic จากวันที่ และใช้**ชื่ออุปกรณ์กับจำนวน
สต็อกจริง**จาก `data/*.json` — ไม่มีอะไรถูกบันทึกลงฐานข้อมูล หน้าเว็บขึ้นป้ายบอกโหมดไว้เสมอ

ใบจองที่ค้างคืน (`overdue`) ถูกนับทับ**ทุกวัน**ตั้งแต่วันจอง ไม่ใช่แค่วันที่จอง
จึงไม่เกิดเหตุการณ์ "ปฏิทินบอกว่าวันถัดไปว่าง ทั้งที่ของยังไม่กลับคลัง"

### ฟอร์มสร้างใบจอง (`js/booking-form.js`)

เปิดได้จาก 3 ทาง: ปุ่ม **จองของวันนี้** ใต้ปฏิทิน · ปุ่ม **จอง**/**ดูคิว** บนการ์ดอุปกรณ์
และอุปกรณ์เสริม · ปุ่ม **จองชุดนี้** ใน Set Builder (แตกชุดเป็นรายชิ้นเสมอ — ระบบไม่มี
"ชุด" เป็นก้อนที่มีสต็อกของตัวเอง)

| | |
|---|---|
| ผู้จอง | ผูกกับบัญชีที่ sign in อัตโนมัติ เลือกแทนคนอื่นไม่ได้ (crew เห็นเฉพาะแถวตัวเอง) |
| สิ่งที่บันทึก | ชื่องาน (จำเป็น) · สถานที่ · วันที่ · หมายเหตุ · รายการอุปกรณ์พร้อมจำนวน |
| เพดานจำนวน | อ่านจาก `item_availability_between(วันนั้น)` — **ก้อนเดียวกับที่ trigger ใช้ตัดสิน** จึงไม่เจอ "หน้าเว็บบอกว่าเหลือ แต่กดจองแล้วโดนปฏิเสธ" |
| ของที่ยังไม่ระบุจำนวน | ปุ่ม `+` ปิด พร้อมข้อความ "ยังไม่ระบุจำนวน — จองไม่ได้" และบอกต่อว่าต้องให้ admin เติมจำนวนก่อน |
| วันนี้เต็มแล้ว | ปุ่ม `+` ปิด และบอกว่าถูกจองเต็มแล้วในวันที่เท่าไร — แต่การ์ดข้างนอกยังเปลี่ยนเป็น "ดูคิว" ให้ไปดูวันอื่นที่ว่างได้ |
| สร้างใบจอง | ยิง `create_booking()` ทีเดียวจบทั้งใบจองและรายการ ถ้ารายการไหนถูกปฏิเสธจะ rollback ทั้งก้อน ไม่เหลือใบจองครึ่งใบค้างในระบบ |
| ข้อความ error | โชว์ข้อความไทยจาก trigger ตามจริง ไม่แปลหรือย่อเอง |
